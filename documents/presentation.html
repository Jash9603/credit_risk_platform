Business Context

Why credit default prediction matters

  • 01A bank approves loans without knowing, upfront, which applicants will struggle to repay — every default is a direct financial loss.
  • 02A blanket accuracy metric is misleading here: with only ~8% of applicants defaulting, a model that always predicts "no default" looks 92% accurate while being useless.
  • 03Risk officers need a *reason*, not just a score — a rejected applicant, and any regulator, can ask "why," and "the model said so" is not an acceptable answer.
  • 04Policy teams think in rules ("reject if X and Y"), not probabilities — the model's judgment needs to be translated into that language to be actionable.
  • 05Analysts who are not SQL-fluent still need to interrogate the data directly — "how many applicants with bad bureau debt also defaulted?" shouldn't require an engineer.
  • 06All of this has to be one coherent, deployed system — a notebook full of separate scripts is not something a bank could actually put in front of a loan officer.

Six findings that shaped the build

  1. Most missing data is optional apartment/building detail — not a data error.
  2. External credit scores (EXT_SOURCE 1/2/3) are the strongest single predictor of default.
  3. Younger applicants default roughly 2x more than the 56–65 group.
  4. Unemployed/maternity-leave and lower-education segments run well above average risk.
  5. The DAYS_EMPLOYED "365243" placeholder is itself a useful, lower-risk retiree signal.
  6. Zero bureau credit history is a mild risk signal — "unknown" isn't the same as "safe".

Class imbalance handling

Why LightGBM over XGBoost

Both now handle categorical features and histogram-based splitting natively. LightGBM does both out of the box for this dataset's mix of categorical and high-cardinality columns with no extra configuration — a convenience call, not a capability gap.

Talk-to-Data

Natural language, real SQL, grounded answers

Token optimization

  • Compact schema card (columns + types only), not verbose per-field docs.
  • Rows capped at 200 by the DB; only 50 ever reach the answer-writer.
  • Follow-ups are condensed to one standalone question by a dedicated small step, instead of replaying full history every turn.

Hallucination mitigation

  • Schema grounded in Postgres's real information_schema + real categorical values — not memorized guesses.
  • Every SQL statement actually executes read-only before anything is treated as fact.
  • Answer synthesis is closed-book: only the real returned rows, never a number invented to fill a gap.
  • Three defense-in-depth SQL safety layers: prompt rules, AST validator (SELECT-only, table allowlist), READ ONLY transaction.

Deployment

One command, fully containerized

$ docker compose up --build ✓ db Healthy ✓ api Started ✓ frontend Started

What happens automatically

  1. Postgres starts and passes its healthcheck.
  2. API waits on that healthcheck, then idempotently ingests all 7 tables.
  3. Model + EDA charts are already baked into the API image — nothing retrains.
  4. Frontend is a static build served by nginx, API URL baked in at build time.

Results summary

Delivered

  • ✓EDA with 8 documented business insights

  • ✓SHAP explainability on every prediction
  • ✓16 rules derived from the model's own behavior
  • ✓NL-to-SQL chatbot, grounded & validated
  • ✓Multi-section dashboard UI, dockerized end to end

Known limitations

  • Rules lean heavily on the two external bureau scores.
  • Metrics are out-of-fold CV estimates — no labeled held-out test set exists.
  • No hyperparameter search beyond early-stopping tree count.
  • Single LLM provider (OpenAI) for the chatbot, not provider-agnostic.

Full reasoning behind every design choice is in DECISIONS.md in the repository.
